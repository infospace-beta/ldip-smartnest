## Manager settings

Open **Dashboard → Automations**. The master switch and individual controls are optional. Turning them off stops rule-based approvals, automatic reassignment, scheduled reminders and automatic inspection creation. Manual actions still create their linked records and notify the intended recipients.

The defaults are:

- Provider response window: **24 hours**.
- Inspection advance notice: **14 days**.
- Routine inspection frequency: **90 days**.
- Working hours: **09:00–17:00, Monday–Friday**.
- Maximum routine selections: **one eligible occupied home per day**.
- Routine repair auto-approval: **off**, with a spending limit of zero until configured.

Managers enter their standard category estimates and each provider’s service categories. Automatic approval uses those manager-controlled estimates, within the spending limit. Requests needing a quotation return for approval. Random inspections select homes; they do not authorize unannounced visits. Proposed appointments follow the configured notice period and working hours.

## Sign-in configuration

### Enabled and checked

- Existing email sign-in and Gmail SMTP configuration were retained.
- The sign-in email template now includes both its existing magic link and a one-time code.
- Supabase passkeys were enabled for the existing **localhost** configuration: relying-party ID `localhost`, origin `http://localhost:3000`.
- TOTP authenticator support was already enabled in Supabase. The backend now requires a verified MFA session for admin and manager operational access.
- Password-reset delivery was confirmed for an existing registered account. A local Django-only account cannot receive a Supabase recovery email until its identity is activated and linked.

Admin and manager users should open **Account security**, scan the QR code with their own authenticator app and enter its code. Passkeys can then be registered from the same page. Personal authenticator/passkey enrollment is completed by the account holder.

### Still needs provider setup

| Method | Remaining requirement |
| --- | --- |
| Google sign-in | Configure the Google OAuth client and secret in Supabase. The application button stays disabled until the provider is enabled. |
| Phone one-time codes | Configure and enable the SMS provider in Supabase. Phone verification becomes available in Account security when that provider is enabled. SMS delivery may incur provider charges. |
| Hosted passkeys | Before using passkeys on a hosted domain, configure its relying-party ID and allowed HTTPS origin. The current passkey configuration is for localhost. |

No Google client secret, SMS credentials or personal account passwords were invented or changed. The same login page continues to obtain each user’s role from SmartNest’s backend.

For older local-only accounts, an administrator must verify the correct Supabase identity before using the existing linking command:

```text
python manage.py link_supabase_user person@example.com VERIFIED_SUPABASE_UUID
```

This retains the local account’s approved permissions; it does not assign an account by matching email alone.

Official setup references: [Google](https://supabase.com/docs/guides/auth/social-login/auth-google), [passwordless email](https://supabase.com/docs/guides/auth/auth-email-passwordless), [passkeys](https://supabase.com/docs/guides/auth/passkeys), [MFA](https://supabase.com/docs/guides/auth/auth-mfa).

## Running the update

The new backend dependency is `cryptography==50.0.2`; it is pinned in `backend/requirements.txt`. No new frontend package or browser extension is required.

For another checkout or a hosted deployment, install the backend requirements and apply migrations before serving the updated app:

```text
cd backend
python -m pip install -r requirements.txt
python manage.py migrate
```

Run the automation worker as a separate process:

```text
python manage.py process_smartnest_automations --loop --interval 60
```

A local worker was started in the background. It honors the manager switches and reports its latest check in the settings screen. After a reboot it must be started again. In hosting, supervise this process with automatic restarts. A one-time run uses the same command without `--loop`.

The normal Django API and Next.js frontend still run separately. Deploy both, including the migrations and worker, when publishing the update.

## Confidentiality and existing records

Notice content uses authenticated server-side encryption. This is **server-managed encryption**, not end-to-end encryption. API authorization determines who can receive decrypted notice content. Keep the existing Django signing secret securely backed up: the notice encryption key is derived from it, and changing it requires a planned re-encryption process.

Historical notices had no recipient records. Their contents were encrypted and retained privately rather than guessing who should read them. Historical inspections with unknown tenant ownership remain available within their manager’s portfolio; the migration does not expose them to a guessed tenant. Existing profile-photo and handover-photo edits were preserved.
